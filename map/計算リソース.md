# 計算リソースの地図

> **試験ドメイン対応**
> - Domain 2（回復性 26%）: Auto Scaling、疎結合設計
> - Domain 3（パフォーマンス 24%）: インスタンスタイプ選択、Lambda最適化
> - Domain 4（コスト最適化 20%）: 購入オプション（RI・スポット・Savings Plans）

## なぜ複数のサービスがあるのか

AWSの計算リソースは「どこまで管理を任せるか」の軸で整理できる。

```
自分で管理 ←―――――――――――――――――――→ AWSに任せる

EC2       ECS on EC2   Fargate    Lambda
（OS管理）  （クラスター管理）  （コンテナのみ）  （コードのみ）
```

管理が少ないほど運用コストは下がるが、制御も減る。

---

## EC2

**なぜ存在するか**: クラウド上に「自分のサーバー」を持ちたいから。

**選ぶ理由**:
- OSレベルの設定が必要（特定のソフトウェア、カーネル設定など）
- 長時間動き続けるアプリケーション
- 既存のオンプレミスをそのまま移行したい

**試験で問われる判断**:
- `リザーブドインスタンス` → 1〜3年使うと確実にわかっているとき（最大72%割引）
- `スポットインスタンス` → 中断されてもいいバッチ処理（最大90%割引）
- `オンデマンド` → 予測できない短期利用

**インスタンスタイプの選び方**:
| プレフィックス | 用途 |
|---|---|
| t系 (t3, t4g) | 汎用・開発環境（バースト可能） |
| m系 (m5, m6i) | 汎用・本番環境 |
| c系 (c5, c6g) | CPU集約（計算処理） |
| r系 (r5, r6g) | メモリ集約（インメモリDB） |
| i系 | ストレージ集約（高速I/O） |

---

## Lambda

**なぜ存在するか**: サーバーを意識せずコードだけ実行したいから。

**選ぶ理由**:
- イベント駆動（S3にファイルが来たら処理、APIリクエストが来たら処理）
- 実行時間が短い（最大15分）
- 使った分だけ課金（待機中はコストゼロ）

**試験で問われる判断**:
- Lambda vs EC2 → 常時稼働 or 大量CPUが必要ならEC2、それ以外はLambdaを検討
- コールドスタートが問題 → `Provisioned Concurrency` で解決
- 処理時間15分超 → Lambdaは使えない → EC2 or Batch or Step Functions

---

## ECS / Fargate

**なぜ存在するか**: Dockerコンテナを本番で動かしたいから。

**ECS on EC2**:
- コンテナのスケジューリングはAWSが管理するが、EC2（ホスト）は自分で管理
- コスト最適化しやすい（スポットインスタンス活用など）

**Fargate**:
- EC2（ホスト）も含めてAWSが管理
- サーバーのことを完全に考えなくていい
- 少し割高だが運用が楽

**試験で問われる判断**:
- EC2 vs Fargate → インフラ管理したくないならFargate
- Kubernetes使いたい → EKS（ECSのK8s版）

## よく試験に出る比較

### EC2 vs Lambda
| | EC2 | Lambda |
|---|---|---|
| 実行時間 | 無制限 | 最大15分 |
| 起動 | 分単位 | ミリ秒（コールドスタートあり） |
| コスト | 稼働時間課金 | 実行回数・時間課金 |
| 向いている | 常時稼働・重い処理 | イベント駆動・短い処理 |

### ECS vs Lambda
- 長時間コンテナプロセス → ECS/Fargate
- イベント駆動・短時間 → Lambda（Lambdaもコンテナイメージ対応）
