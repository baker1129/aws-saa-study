# データベースの地図

> **試験ドメイン対応**
> - Domain 2（回復性 26%）: RDSマルチAZ、Auroraフェイルオーバー
> - Domain 3（パフォーマンス 24%）: リードレプリカ、ElastiCache、DAX
> - Domain 4（コスト最適化 20%）: DynamoDBオンデマンド vs プロビジョンド、RDS RI

## なぜ複数のDBサービスがあるのか

「どんなデータを、どう使うか」でDBの種類が変わる。

```
         リレーショナル          NoSQL            分析
         （RDS・Aurora）   （DynamoDB）      （Redshift）

データ     行・列のテーブル   柔軟なドキュメント  集計・レポート用
向いてる   トランザクション   大量・高速アクセス  大量データの分析
例         注文管理・認証DB   ゲームスコア・カート  売上分析・ログ集計
```

---

## RDS（Relational Database Service）

**なぜ存在するか**: MySQLやPostgreSQLなどのRDBMSをサーバー管理なしで使うため。

**対応エンジン**: MySQL / PostgreSQL / MariaDB / Oracle / SQL Server / Aurora

**特徴**:
- OSパッチ・バックアップ・フェイルオーバーをAWSが自動管理
- マルチAZ: 別AZにスタンバイを自動で用意（可用性向上）
- リードレプリカ: 読み込み専用のコピー（読み込み性能向上）

**試験で問われる判断**:
- 「可用性を高めたい」→ `マルチAZ`（書き込みのフェイルオーバー）
- 「読み込みが重い」→ `リードレプリカ`（読み込みの分散）
- マルチAZとリードレプリカは別物（混同しやすい）

---

## Aurora

**なぜ存在するか**: RDSより高速・高可用なMySQLまたはPostgreSQL互換DBが欲しいから。

**特徴**:
- MySQL比5倍、PostgreSQL比3倍の性能（AWS独自最適化）
- ストレージは6コピーを3AZに自動分散（高耐久）
- コストはRDSより高いが性能が要求されるときに使う

**Aurora Serverless v2**:
- アクセスに応じて自動でスケールアップ/ダウン
- アクセスがないときはほぼゼロコスト

**試験で問われる判断**:
- 高性能RDBが必要 → Aurora
- 負荷が予測できない → Aurora Serverless
- コスト重視・性能要件が緩い → RDS

---

## DynamoDB

**なぜ存在するか**: 大量のリクエストを低レイテンシで捌くNoSQLが必要だから。

**特徴**:
- スキーマレス（テーブルの列を事前定義しなくていい）
- 1ミリ秒以下のレイテンシ
- 自動スケール（急激なアクセス増にも対応）
- サーバーレス（管理不要）

**重要な概念**:
- `パーティションキー`: データの振り分けキー（分散の基本）
- `ソートキー`: 同じパーティション内での並び順
- `GSI（グローバルセカンダリインデックス）`: 別のキーでの検索を可能にする

**DAX（DynamoDB Accelerator）**:
- DynamoDBのインメモリキャッシュ
- マイクロ秒レベルのレイテンシが必要なとき

**試験で問われる判断**:
- RDS vs DynamoDB → 複雑なJOINや厳密なトランザクションが必要ならRDS、そうでなければDynamoDBも検討
- 「1ミリ秒以下」「大量トラフィック」「スキーマレス」→ DynamoDB

---

## Redshift

**なぜ存在するか**: 数百TB〜PBのデータに対して高速な分析クエリを実行するため。

**特徴**:
- データウェアハウス（OLAP）
- 列指向ストレージ（集計クエリが速い）
- S3との連携（Redshift Spectrum でS3のデータも直接クエリ可能）

**試験で問われる判断**:
- 「大量データの集計・分析・レポート」→ Redshift
- リアルタイムのトランザクション処理 → Redshift は不向き（RDS/Auroraを使う）

---

## ElastiCache

**なぜ存在するか**: DBへのアクセスを減らして速度を上げるインメモリキャッシュ。

**エンジン**:
- **Redis**: 永続化あり、レプリケーションあり、複雑なデータ構造対応
- **Memcached**: シンプル・高速・永続化なし

**試験で問われる判断**:
- 「DBが遅い・負荷が高い」→ ElastiCacheでよく読むデータをキャッシュ
- セッション管理 → Redis（永続化できる）
- シンプルなキャッシュ → Memcached

## よく試験に出る比較

### RDS vs DynamoDB vs Redshift
| | RDS / Aurora | DynamoDB | Redshift |
|---|---|---|---|
| 種類 | RDBMS (OLTP) | NoSQL | データウェアハウス (OLAP) |
| 向いてる操作 | トランザクション | 大量単純アクセス | 集計・分析 |
| スケール | 垂直スケール中心 | 自動水平スケール | クラスター拡張 |

### マルチAZ vs リードレプリカ
| | マルチAZ | リードレプリカ |
|---|---|---|
| 目的 | 可用性（フェイルオーバー） | 読み込みパフォーマンス向上 |
| 読み込みに使える？ | 原則不可 | はい |
| 自動フェイルオーバー | あり | なし |
