# Domain 3: 高パフォーマンスなアーキテクチャの設計（24%）

「速くする」「スケールさせる」ための設計。
キーワード: キャッシュ、スループット、レイテンシ、水平スケール

---

## タスク3.1: 高パフォーマンスなストレージを選択する

**意識すること**: アクセスパターン（頻度・速度・共有の有無）でストレージを選ぶ。

### 問われる判断

**S3のパフォーマンス**
- デフォルトでプレフィックスごとに秒間3,500 PUT / 5,500 GET
- さらに速くしたい → プレフィックスを分散させる（キーの先頭を多様化）
- 別リージョンのユーザーへ速く届けたい → `CloudFront` または `S3 Transfer Acceleration`

**EBSのパフォーマンス**
- 高IOPS必要 → `io2 Block Express`
- コスト重視の汎用 → `gp3`（IOPSを個別に設定可能）
- シーケンシャル読み書き（ビッグデータ）→ `st1`

**試験でよく出るパターン**:
- 「EC2間でファイルを共有しつつ高スループット」→ EFS
- 「大量データを安く長期保存」→ S3 + ライフサイクルポリシー

## タスク3.2: 高パフォーマンスな計算リソースを選択する

**意識すること**: ワークロードの特性（常時稼働か・突発か・CPU集約か）で選ぶ。

### 問われる判断

**EC2のスケーリング**
- 垂直スケール（スケールアップ）: インスタンスサイズを大きくする → 停止が必要・限界あり
- 水平スケール（スケールアウト）: 台数を増やす → Auto Scaling で自動化 → こちらが基本

**Lambda のパフォーマンスチューニング**
- メモリを増やす → CPUパワーも比例して増加（Lambda はメモリ量でCPUが決まる）
- コールドスタートを防ぐ → `Provisioned Concurrency`
- 10GB メモリ・15分以内の処理 → Lambdaの上限

**試験でよく出るパターン**:
- 「突発的なトラフィックに対応したい」→ Auto Scaling + ALB
- 「Lambdaのレイテンシが高い（初回リクエスト）」→ Provisioned Concurrency
- 「重いバッチ処理を効率化したい」→ AWS Batch または Step Functions

## タスク3.3: 高パフォーマンスなデータベースを選択する

**意識すること**: 読み込み・書き込み・検索の特性に合わせてDBとキャッシュを組み合わせる。

### 問われる判断

**RDS/Aurora のパフォーマンス向上**
- 読み込みが重い → `リードレプリカ`（読み込みをレプリカに分散）
- 接続が多すぎる → `RDS Proxy`（接続プールで管理、Lambda との相性良）

**DynamoDB のパフォーマンス**
- ミリ秒以下が必要 → `DAX`（DynamoDB Accelerator / インメモリキャッシュ）
- アクセスが集中する「ホットパーティション」問題 → パーティションキーの設計を見直す

**キャッシュ戦略**
```
アプリ → [ElastiCache] → ヒット → 返す
            ↓ ミス
           [DB] → 取得 → キャッシュに保存 → 返す
```
- `キャッシュアサイド（Lazy Loading）`: ミスしたときだけDBから取得
- `ライトスルー`: DBに書くと同時にキャッシュも更新

**Redis vs Memcached**
| | Redis | Memcached |
|---|---|---|
| 永続化 | あり | なし |
| レプリケーション | あり | なし |
| 複雑なデータ構造 | あり（リスト・セット等） | なし |
| 向いてる用途 | セッション管理・ランキング | シンプルなキャッシュ |

**試験でよく出るパターン**:
- 「RDSの読み込みが遅い」→ リードレプリカ or ElastiCache
- 「Lambda が RDS に大量接続してエラー」→ RDS Proxy
- 「DynamoDB をさらに高速化したい」→ DAX

## タスク3.4: 高パフォーマンスなネットワークを選択する

**意識すること**: ユーザーの近くで処理する・専用線でスループットを上げる。

### 問われる判断

**CloudFront vs Global Accelerator**
| | CloudFront | Global Accelerator |
|---|---|---|
| 主な用途 | コンテンツキャッシュ配信 | TCP/UDPトラフィックの高速化 |
| キャッシュ | あり | なし |
| 固定IP | なし | あり（Anycast IP） |
| 向いてる | 静的コンテンツ・動画 | ゲーム・IoT・動的コンテンツ |

**試験でよく出るパターン**:
- 「静的コンテンツを世界中に高速配信」→ CloudFront
- 「動的コンテンツ・APIのグローバル高速化」→ Global Accelerator
- 「固定IPでグローバル高速化」→ Global Accelerator

---

## タスク3.5: 高パフォーマンスなデータ処理を選択する

**意識すること**: リアルタイムか・バッチか・変換が必要か。

| サービス | 役割 |
|---|---|
| Kinesis Data Streams | リアルタイムストリームデータの取り込み・処理 |
| Kinesis Data Firehose | ストリームデータをS3/Redshift等に自動配信（変換も可） |
| SQS | 非同期キュー処理 |
| EMR | Hadoop/Sparkの大規模データ処理 |
| Glue | ETL（抽出・変換・ロード）のサーバーレス処理 |
| Athena | S3上のデータをSQLで直接クエリ |

**試験でよく出るパターン**:
- 「IoTデータをリアルタイムで処理」→ Kinesis Data Streams + Lambda
- 「ログをS3に継続的に保存して分析」→ Kinesis Firehose → S3 → Athena
- 「S3のCSVをSQLで分析したい」→ Athena
