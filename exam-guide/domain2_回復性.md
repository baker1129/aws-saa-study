「壊れても動き続ける」「障害から素早く回復する」ための設計。
キーワード: 高可用性（HA）、フォールトトレラント、疎結合、スケーラビリティ

## タスク2.1: スケーラブルで疎結合なアーキテクチャを設計する

**意識すること**: コンポーネントを直接繋げると、片方が壊れたとき全体が止まる。間に「バッファ」を入れる。

### 疎結合のパターン

**メッセージキュー（SQS）**
```
送信側 → [SQS] → 受信側
```
- 送信側と受信側が独立してスケール可能
- 受信側が落ちても、メッセージはキューに残る
- `標準キュー`: 高スループット・順序保証なし
- `FIFOキュー`: 順序保証あり・重複なし（スループット制限あり）

**通知・ファンアウト（SNS）**
```
イベント → [SNS] → Lambda
                  → SQS
                  → メール
```
- 1つのイベントを複数の送信先に同時配信
- SNS + SQS の組み合わせ（ファンアウトパターン）が頻出

**イベント駆動（EventBridge）**
- AWSサービスのイベント（EC2起動、S3アップロード等）をトリガーに処理を実行
- 「S3にファイルが来たらLambdaで処理」→ S3イベント通知 または EventBridge

**API Gateway**
- HTTPリクエストをLambdaやバックエンドに繋ぐ
- スロットリング・認証・HTTPS対応をここで管理

**試験でよく出るパターン**:
- 「注文が来たとき、在庫サービスとメール通知を同時に動かしたい」→ SNS ファンアウト
- 「処理が追いつかないときメッセージを失いたくない」→ SQS
- 「サーバーレスAPIを作りたい」→ API Gateway + Lambda

## タスク2.2: 高可用性・フォールトトレラントなアーキテクチャを設計する

**意識すること**: 単一障害点（SPOF）をなくす。何かが壊れても自動で切り替わる設計。

### マルチAZ構成

```
AZ-a              AZ-b
[EC2]   ←ALB→   [EC2]
[RDS Primary]    [RDS Standby]
```

- 「1つのAZが落ちても動き続ける」= マルチAZが基本
- RDS マルチAZ: スタンバイへの自動フェイルオーバー（通常1〜2分）
- ELB: 自動でトラフィックを正常なAZに振り分け

### Auto Scaling

- EC2の台数を負荷に応じて自動増減
- スケールアウト（台数増加）とスケールイン（台数削減）
- `起動テンプレート`でEC2の設定を定義
- スケーリングポリシーの種類:
  - `ターゲット追跡`: CPU使用率70%を維持するよう自動調整（最もシンプル）
  - `ステップスケーリング`: 閾値に応じて段階的に増減
  - `スケジュール`: 時間帯で台数を変える

### 災害復旧（DR）戦略

RTO（目標復旧時間）と RPO（目標復旧時点）のトレードオフ。

```
コスト低 ←―――――――――――――――――→ コスト高
復旧遅い ←―――――――――――――――――→ 復旧速い

バックアップ&リストア → パイロットライト → ウォームスタンバイ → アクティブ/アクティブ
  数時間〜               数十分〜             数分〜                ほぼゼロ
```

| 戦略 | 内容 |
|---|---|
| バックアップ&リストア | データだけ別リージョンに保存。復旧時に構築 |
| パイロットライト | 最小限のコアシステムだけ起動済み |
| ウォームスタンバイ | 縮小版の本番環境が常時起動済み |
| アクティブ/アクティブ | 2リージョンが同時に本番稼働（Route53でルーティング） |

**試験でよく出るパターン**:
- 「障害時に自動でフェイルオーバーしたい（RDS）」→ マルチAZ
- 「読み込み負荷を下げたい（RDS）」→ リードレプリカ（マルチAZとは別）
- 「RTO/RPOを最小にしたい」→ アクティブ/アクティブ or ウォームスタンバイ
- 「S3のデータを別リージョンに複製したい」→ クロスリージョンレプリケーション（CRR）
